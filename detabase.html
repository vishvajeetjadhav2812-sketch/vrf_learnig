01

What is a DBMS?

Where data-driven software begins: what a DBMS actually does, and why it replaced flat file systems.

A Database Management System (DBMS) is software that creates, stores, manages, and retrieves data while enforcing rules about that data's structure, consistency, and access. Rather than an application talking directly to raw files, it talks to the DBMS, which handles storage layout, concurrent access, integrity checks, and recovery on its behalf.

Early data-driven applications in the 1960s–70s stored records directly in flat files (think: a folder of .dat files, each read and written by custom application code). As systems grew, this became unsustainable — leading to the rise of DBMS software such as IBM's IMS, then relational systems following Edgar Codd's 1970 paper on the relational model, which underpins SQL databases today.

File System vs DBMS

AspectFile SystemDBMS
Data redundancyHigh — same data often duplicated across filesMinimized via normalization & shared storage
Data integrityEnforced manually in application codeEnforced by constraints (PK, FK, CHECK, etc.)
Concurrent accessProne to conflicts, no built-in lockingManaged via locking / MVCC and isolation levels
QueryingCustom code per queryDeclarative query language (SQL)
SecurityOS-level file permissions onlyFine-grained user & role-based privileges
Backup & recoveryManual, application-specificBuilt-in transaction logs, point-in-time recovery

Why it matters: A DBMS gives you data independence, controlled redundancy, integrity enforcement, backup/recovery, and multi-user concurrency — the foundation every serious application (banking, e-commerce, healthcare records) is built on.

02

Types of Databases

Not every workload fits neatly into rows and columns — here's the landscape.

Relational (RDBMS)

Data stored in tables with predefined schemas, related via keys. Strong consistency guarantees (ACID). Examples: PostgreSQL, MySQL, Oracle, SQL Server.

NoSQL

Schema-flexible stores optimized for scale and specific access patterns: document (MongoDB), key-value (Redis, DynamoDB), wide-column (Cassandra), and graph (Neo4j) databases.

Object-Oriented (OODBMS)

Stores data as objects, mirroring object-oriented programming — attributes and behaviors bundled together. Examples: db4o, ObjectDB. Useful when app objects map awkwardly to tables.

Distributed Databases

Data is partitioned and/or replicated across multiple physical nodes for scalability and fault tolerance — e.g. CockroachDB, Google Spanner, Cassandra clusters.

03

DBMS Architecture

The 3-schema (ANSI/SPARC) architecture separates how data is stored from how it's used.

LevelAlso calledConcern
Internal / PhysicalStorage levelHow data is physically stored — file organization, indexing structures, compression.
Conceptual / LogicalCommunity levelWhat data is stored and the relationships among it, independent of physical storage — this is where the schema of tables lives.
External / ViewUser levelWhat a specific user or application sees — customized views hiding irrelevant parts of the schema.

Data Independence

  • Logical data independence — you can change the conceptual schema (e.g. add a column) without rewriting external views/applications.
  • Physical data independence — you can change physical storage (e.g. switch storage engine, add an index) without touching the conceptual schema.
04

SQL vs NoSQL

The core trade-off: strict structure and strong consistency vs flexible schema and horizontal scale.

DimensionSQL (Relational)NoSQL (Document / Key-Value)
StructureFixed schema, tables with rows/columnsFlexible schema — JSON documents, key-value pairs
RelationshipsModeled via foreign keys & joinsOften embedded or denormalized
ScalabilityPrimarily vertical (bigger server); horizontal via sharding is harderDesigned for horizontal scale across commodity nodes
Consistency modelACID — strong consistencyBASE — Basically Available, Soft state, Eventually consistent
Query languageSQL — standardized, powerful joinsVaries by product; often API/query-DSL based
Best forFinancial systems, ERPs, anything needing strict integrity & complex joinsHigh-velocity writes, catalogs, real-time analytics, flexible/evolving data
05

Entity-Relationship (ER) Modeling

Before you write a single CREATE TABLE, you model the real world as entities and relationships.

Entities & Attributes

An entity is a real-world object or concept with independent existence (a Customer, an Order). An attribute describes a property of an entity:

  • Simple — atomic, can't be divided (e.g. age)
  • Composite — can be split into sub-parts (e.g. name → first_name + last_name)
  • Multi-valued — can hold multiple values (e.g. a customer's phone_numbers)
  • Derived — computed from other attributes (e.g. age derived from date_of_birth)

Keys

Key typeDefinition
Super KeyAny set of attributes that uniquely identifies a row (may contain extra, unnecessary attributes).
Candidate KeyA minimal super key — no attribute can be removed without losing uniqueness. A table can have several.
Primary KeyThe candidate key chosen to uniquely identify rows in a table. Cannot be NULL.
Composite KeyA primary/candidate key made of two or more columns together (e.g. order_id + product_id).
Foreign KeyA column (or set) referencing the primary key of another table, enforcing referential integrity.
06

Cardinality & Modality

How many instances of one entity relate to instances of another.

1 : 1

One User has exactly one Passport. Rare — usually merged into a single table unless there's a strong reason to split.

1 : N

One Customer places many Orders. The "many" side holds the foreign key back to the "one" side. Most common relationship type.

N : M

Many Students enroll in many Courses. Requires a junction/bridge table (e.g. Enrollments) holding both foreign keys.

Modality describes whether a relationship is mandatory (minimum 1) or optional (minimum 0) — e.g. an Order must have a Customer (mandatory), but a Customer may have zero Orders (optional).

07

Mapping ER Diagrams to Relational Tables

Turning boxes and diamonds into real CREATE TABLE statements.

  • Each strong entity becomes a table; its attributes become columns; its identifier becomes the primary key.
  • A 1:N relationship is implemented by placing the "one" side's primary key as a foreign key on the "many" side.
  • An N:M relationship becomes its own junction table, whose primary key is typically the composite of both foreign keys.
  • Multi-valued attributes become their own child table (you can't store a list in one relational column cleanly).
mapping_example.sql
-- 1:N mapping — Customer places many Orders
CREATE TABLE customers (
    customer_id   INT PRIMARY KEY,
    full_name     VARCHAR(100)
);
 
CREATE TABLE orders (
    order_id      INT PRIMARY KEY,
    customer_id   INT,
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);
 
-- N:M mapping — Students enroll in Courses (junction table)
CREATE TABLE enrollments (
    student_id    INT,
    course_id     INT,
    enrolled_on   DATE,
    PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (student_id) REFERENCES students(student_id),
    FOREIGN KEY (course_id) REFERENCES courses(course_id)
);
08

SQL Command Classification

Every SQL statement falls into one of four families.

DDL

Data Definition Language

Defines/modifies structure.

CREATE · ALTER · DROP · TRUNCATE
DML

Data Manipulation Language

Works with the data itself.

SELECT · INSERT · UPDATE · DELETE
DCL

Data Control Language

Manages permissions.

GRANT · REVOKE
TCL

Transaction Control Language

Manages transaction boundaries.

COMMIT · ROLLBACK · SAVEPOINT
command_families.sql
-- DDL: define structure
ALTER TABLE products ADD COLUMN stock_qty INT DEFAULT 0;
DROP TABLE IF EXISTS temp_logs;
TRUNCATE TABLE session_cache;
 
-- DML: manipulate data
INSERT INTO products (name, price) VALUES ('Wireless Mouse', 19.99);
UPDATE products SET price = 17.99 WHERE name = 'Wireless Mouse';
DELETE FROM products WHERE stock_qty = 0;
 
-- DCL: manage access
GRANT SELECT, INSERT ON products TO app_user;
REVOKE INSERT ON products FROM app_user;
 
-- TCL: manage transaction boundaries
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
SAVEPOINT before_credit;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

Data Types & Constraints

Constraints are how the database enforces business rules automatically, rather than relying on the application to always get it right.

ConstraintPurpose
NOT NULLColumn must always have a value.
UNIQUENo two rows may share the same value in this column.
PRIMARY KEYCombines NOT NULL + UNIQUE; identifies each row.
FOREIGN KEYValue must exist in the referenced table's key column.
CHECKValue must satisfy a boolean expression, e.g. CHECK (price > 0).
DEFAULTValue used automatically when none is supplied on INSERT.
constraints_demo.sql
CREATE TABLE products (
    product_id   SERIAL PRIMARY KEY,
    sku          VARCHAR(20)  NOT NULL UNIQUE,
    name         VARCHAR(120) NOT NULL,
    price        DECIMAL(10,2) NOT NULL CHECK (price > 0),
    in_stock     BOOLEAN DEFAULT TRUE,
    created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

Filtering, Sorting & Aggregation

The workhorse clauses you'll write hundreds of times: WHERE, ORDER BY, GROUP BY, HAVING.

basic_queries.sql
-- Filtering + sorting
SELECT name, price
FROM products
WHERE price > 15 AND in_stock = TRUE
ORDER BY price DESC;
 
-- Aggregation: revenue per category
SELECT category, COUNT(*) AS num_products,
       AVG(price) AS avg_price,
       SUM(price) AS total_value
FROM products
GROUP BY category
HAVING COUNT(*) > 2
ORDER BY total_value DESC;

▸ sample result of the query above

categorynum_productsavg_pricetotal_value
Electronics584.20421.00
Home & Kitchen329.9989.97

WHERE vs HAVING: WHERE filters rows before grouping; HAVING filters groups after aggregation. You cannot use an aggregate function like COUNT() inside WHERE.

Full Schema: E-Commerce Database

A complete, runnable schema — Users, Products, Orders — used in later examples throughout this guide.

ecommerce_schema.sql
CREATE TABLE users (
    user_id      SERIAL PRIMARY KEY,
    full_name    VARCHAR(100) NOT NULL,
    email        VARCHAR(150) NOT NULL UNIQUE,
    signup_date  DATE DEFAULT CURRENT_DATE
);
 
CREATE TABLE products (
    product_id   SERIAL PRIMARY KEY,
    name         VARCHAR(120) NOT NULL,
    category     VARCHAR(60),
    price        DECIMAL(10,2) NOT NULL CHECK (price > 0),
    stock_qty    INT NOT NULL DEFAULT 0
);
 
CREATE TABLE orders (
    order_id     SERIAL PRIMARY KEY,
    user_id      INT NOT NULL,
    order_date   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    status       VARCHAR(20) DEFAULT 'pending',
    FOREIGN KEY (user_id) REFERENCES users(user_id)
);
 
-- Junction table: which products are in which order, and how many
CREATE TABLE order_items (
    order_id     INT NOT NULL,
    product_id   INT NOT NULL,
    quantity     INT NOT NULL CHECK (quantity > 0),
    unit_price   DECIMAL(10,2) NOT NULL,
    PRIMARY KEY (order_id, product_id),
    FOREIGN KEY (order_id) REFERENCES orders(order_id),
    FOREIGN KEY (product_id) REFERENCES products(product_id)
);

SQL Joins

Joins combine rows from two or more tables based on a related column. Click a join type below to see its syntax and Venn diagram.

Returns only rows where the join condition matches in both tables — orders that do have a matching user.

inner_join.sql
SELECT o.order_id, u.full_name, o.status
FROM orders o
INNER JOIN users u ON o.user_id = u.user_id;

Returns all rows from the left table (users), plus matches from the right (orders) — NULL where no order exists.

left_join.sql
SELECT u.full_name, o.order_id
FROM users u
LEFT JOIN orders o ON u.user_id = o.user_id;
-- users with zero orders still appear, with order_id = NULL

Mirror of LEFT JOIN — all rows from the right table (orders), plus matches from the left (users).

right_join.sql
SELECT o.order_id, u.full_name
FROM users u
RIGHT JOIN orders o ON u.user_id = o.user_id;

Returns all rows from both tables, matched where possible, NULLs where not. Not supported natively in MySQL — emulate with UNION.

full_outer_join.sql
SELECT u.full_name, o.order_id
FROM users u
FULL OUTER JOIN orders o ON u.user_id = o.user_id;

Returns the Cartesian product — every row of table A paired with every row of table B. No ON clause. Use deliberately (e.g. generating combinations).

cross_join.sql
SELECT s.size_label, c.color_name
FROM sizes s
CROSS JOIN colors c;
-- 4 sizes x 5 colors = 20 rows (every combination)

Joins a table to itself, using aliases to treat it as two logical tables — common for hierarchical data (an employee's manager).

self_join.sql
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.employee_id;

Subqueries & CTEs

Queries nested inside other queries — and their more readable cousin, the Common Table Expression.

nested_subquery.sql
-- Users who have never placed an order
SELECT full_name
FROM users
WHERE user_id NOT IN (
    SELECT user_id FROM orders
);
correlated_subquery.sql
-- Products priced above their category's average
SELECT p1.name, p1.price, p1.category
FROM products p1
WHERE p1.price > (
    SELECT AVG(p2.price)
    FROM products p2
    WHERE p2.category = p1.category
);
cte_example.sql
-- CTE: total spend per user, then filter on it — far more readable than nesting
WITH user_totals AS (
    SELECT o.user_id, SUM(oi.quantity * oi.unit_price) AS total_spent
    FROM orders o
    JOIN order_items oi ON o.order_id = oi.order_id
    GROUP BY o.user_id
)
SELECT u.full_name, ut.total_spent
FROM user_totals ut
JOIN users u ON u.user_id = ut.user_id
WHERE ut.total_spent > 500
ORDER BY ut.total_spent DESC;

Why Normalize?

Normalization organizes columns and tables to minimize redundancy and prevent three classic anomalies.

Insertion Anomaly

You can't add a new product until it has an order, because product info is only stored alongside order rows.

Deletion Anomaly

Deleting the only order for a customer accidentally erases all record of that customer, since their data wasn't stored independently.

Update Anomaly

A customer's address is duplicated across 20 order rows — updating it means editing all 20, or risking inconsistent data.

Transactions & ACID Properties

A transaction groups multiple statements into one all-or-nothing unit of work — the classic example is a bank transfer.

A

Atomicity

All statements in the transaction succeed, or none do.

Debit $100 from A, credit $100 to B — if the credit fails, the debit rolls back too.
C

Consistency

A transaction moves the DB from one valid state to another, never violating constraints.

Total money in the system before = total after the transfer.
I

Isolation

Concurrent transactions don't see each other's uncommitted changes.

Two simultaneous transfers from account A don't both read the same stale balance.
D

Durability

Once committed, changes survive a crash — written to durable storage.

Power fails right after COMMIT — the transfer is still there on restart.
bank_transfer.sql
BEGIN;
 
UPDATE accounts SET balance = balance - 100 WHERE account_id = 'A';
UPDATE accounts SET balance = balance + 100 WHERE account_id = 'B';
 
-- if either UPDATE fails or a constraint is violated:
ROLLBACK;
-- otherwise:
COMMIT;

Indexing & Query Optimization

An index trades extra storage and slower writes for dramatically faster reads.

B-Tree Indexes

Most relational databases index using a B-Tree (balanced tree): a sorted structure where lookups, inserts, and range scans all run in O(log n) time, instead of scanning every row (O(n)). A query like WHERE email = 'x@y.com' on an indexed column jumps straight to the matching leaf node rather than reading the whole table.

Clustered Index

Determines the physical storage order of table rows. There can be only one per table (often the primary key) — the table is the index.

Non-Clustered Index

A separate structure holding indexed column values plus pointers back to the actual rows. A table can have many.

indexing.sql
-- Speeds up lookups & sorts by email
CREATE INDEX idx_users_email ON users(email);
 
-- Composite index — helps queries filtering on both columns together
CREATE INDEX idx_orders_user_date ON orders(user_id, order_date);
 
-- Inspect the query plan to see if an index is actually used
EXPLAIN SELECT * FROM users WHERE email = 'x@y.com';

Index overhead: Every index speeds up reads but slows down INSERT/UPDATE/DELETE (the index itself must be updated) and consumes extra disk space. Index columns that are frequently filtered, joined, or sorted on — not every column.

Views, Stored Procedures, Triggers & Security

Tools for encapsulating logic close to the data — and protecting that data from misuse.

view_example.sql
-- A view: a saved, reusable query that looks like a table
CREATE VIEW high_value_orders AS
SELECT o.order_id, u.full_name, SUM(oi.quantity * oi.unit_price) AS order_total
FROM orders o
JOIN users u ON o.user_id = u.user_id
JOIN order_items oi ON o.order_id = oi.order_id
GROUP BY o.order_id, u.full_name
HAVING SUM(oi.quantity * oi.unit_price) > 1000;
procedure_and_trigger.sql
-- Stored procedure: reusable server-side logic
CREATE PROCEDURE place_order(IN p_user_id INT, IN p_product_id INT, IN p_qty INT)
BEGIN
    INSERT INTO orders (user_id) VALUES (p_user_id);
    INSERT INTO order_items (order_id, product_id, quantity, unit_price)
    VALUES (LAST_INSERT_ID(), p_product_id, p_qty,
            (SELECT price FROM products WHERE product_id = p_product_id));
END;
 
-- Trigger: automatically decrement stock after an order item is inserted
CREATE TRIGGER trg_reduce_stock
AFTER INSERT ON order_items
FOR EACH ROW
BEGIN
    UPDATE products
    SET stock_qty = stock_qty - NEW.quantity
    WHERE product_id = NEW.product_id;
END;

SQL Injection Prevention

Never concatenate user input directly into SQL strings. Use parameterized queries / prepared statements, so input is always treated as data, never executable code.

safe_vs_unsafe.sql
-- UNSAFE: string concatenation lets input become SQL code
-- e.g. input: ' OR '1'='1
-- query = "SELECT * FROM users WHERE email = '" + input + "'"
 
-- SAFE: parameterized query — input is always data, never code
SELECT * FROM users WHERE email = ?;

User Privileges

Grant only the minimum access a role needs (principle of least privilege) — an application's read-only reporting user shouldn't hold DELETE rights.

privileges.sql
CREATE ROLE reporting_readonly;
GRANT SELECT ON orders, order_items, products
  TO reporting_readonly;
GRANT reporting_readonly TO analytics_user;
